# 在线双人大厅实施计划

## 目标

在现有 GitHub Pages 游戏中增加“在线双人”入口。玩家无需注册账号；房主创建临时房间并得到六位房间号，另一位玩家输入房间号加入。应用不保存名字、牌局、战绩或聊天记录，房间结束或过期后销毁。

现有“人机对战”和“本地双人”继续使用当前离线引擎。在线模式复用相同规则和界面，但由服务端维护唯一的权威牌局状态，避免暗牌泄露、双方状态不同步及客户端直接修改结果。

## 推荐架构

- **前端：** GitHub Pages，继续发布当前静态站点。
- **房间服务：** Cloudflare Worker。
- **临时状态：** 每个房间对应一个 Durable Object，只在大厅和牌局存活期间保留状态。
- **通信：** 浏览器通过 WebSocket 向房间提交动作并接收事件与脱敏后的局面。
- **持久化：** 不建立用户、牌局或战绩数据库。浏览器仅在 `sessionStorage` 保存本次房间的重连令牌。

## 玩家流程

1. 主菜单显示“人机对战”“本地双人”“在线双人”。
2. 在线双人页面提供“创建房间”和“加入房间”。
3. 房主先设置地图、规则、名字、徽记和势力，然后创建房间。
4. 服务端返回六位房间号；等待页可复制房间号和邀请链接。
5. 客人输入房间号，设置自己的名字、徽记和势力后加入。
6. 两个席位就绪后，由房主开始；开始后规则配置锁定。
7. 短暂断线时使用服务端签发的随机席位令牌重连。超过重连期限后允许对手结束房间。
8. 牌局结束、双方离开或房间过期后销毁状态。

## 服务端职责

- 生成牌库、洗牌、发牌和随机结果。
- 只向每名玩家发送其有权查看的状态；对手暗牌只发送牌背和数量。
- 验证部署、翻牌、策略、补给、驻军、地图移动和胜负判定。
- 为每个动作分配递增序号，拒绝重复、越序和非当前玩家的动作。
- 生成六位房间号、不可猜测的房主/客人席位令牌，并限制尝试频率。
- 限制每个房间两个玩家；默认关闭观战。
- 大厅闲置 30 分钟过期，进行中房间最长 3 小时；空房经过短暂重连窗口后销毁。

六位房间号只用于寻找房间，不能作为身份凭证。成功创建或加入后，客户端必须使用随机席位令牌；服务端还应限制同一来源连续尝试房间号的频率。

## 状态与协议

客户端消息建议统一为：

```json
{
  "type": "action",
  "room": "384721",
  "seatToken": "server-issued-token",
  "sequence": 18,
  "action": { "type": "attack", "field": "center" }
}
```

服务端响应分为 `lobby`、`snapshot`、`event`、`error`、`opponent_disconnected` 和 `game_over`。`snapshot` 必须按席位生成，不能把完整服务器状态发给浏览器后再依靠界面隐藏暗牌。

## 分阶段交付

### 第一阶段：协议与权威引擎

- 将纯规则引擎整理为浏览器和 Worker 都能调用的模块。
- 定义客户端可见状态、动作协议和错误码。
- 为所有玩家动作增加服务端重放测试和双视角暗牌泄露测试。

### 第二阶段：房间大厅

- 完成创建、加入、就绪、开始和离开房间。
- 加入六位房间号、复制邀请、房间已满及房间不存在提示。
- 完成席位令牌、尝试频率限制和房间自动过期。

### 第三阶段：完整联机牌局

- 接通 WebSocket 动作和事件同步。
- 加入断线提示、3–5 分钟重连及状态快照恢复。
- 覆盖 iPhone、iPad、桌面浏览器和页面切后台再恢复的场景。

### 第四阶段：发布

- 配置 GitHub Pages 的 Worker 地址和允许来源。
- 在测试环境进行长局、重复提交、双端同时操作、网络抖动和断线恢复测试。
- 启用 Cloudflare 请求限制和基础运行监控，再开放正式入口。

## 验收条件

- 两台不同设备可以通过六位房间号完成一整局。
- 任一客户端都无法从网络响应读取对手未公开的牌。
- 刷新或短暂断网后能回到原席位，且不会重复执行动作。
- 房主断线不会立刻销毁仍在进行的牌局。
- 过期房间不能加入，结束后的房间状态不可再次读取。
- 不创建用户档案，不持久保存玩家名称、徽记、牌局内容或结果。

## 暂不包含

首版不包含账号、公开房间列表、匹配队列、排行榜、聊天、观战、录像和跨设备永久存档。这些功能会引入持久化、内容治理或更多隐私处理，应在核心双人连接稳定后单独评估。
